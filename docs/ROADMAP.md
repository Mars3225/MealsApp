# CookAlong — план разработки и учебная программа

Приложение с рецептами, где главная ценность — **режим готовки**: пошаговый чек-лист
с таймерами, которые живут независимо от экрана, на котором ты находишься.

Формат работы: код пишет Макс, Claude объясняет «что и зачем», ревьюит, ловит
грабли. Каждая фаза = отдельная ветка + несколько маленьких коммитов.

---

## 0. Ключевое архитектурное наблюдение

Чек-лист готовки невозможно построить на данных TheMealDB.

`strInstructions` — это один кусок текста («Boil the water, add pasta, cook 10
minutes...»). Чтобы показать пункт «поставить воду на огонь» с таймером на 5 минут,
нужны **структурированные шаги**: у каждого есть тип, текст, длительность,
температура, список задействованных ингредиентов.

Значит источник правды — наша собственная модель данных:

```
Recipe (id, title, image, servings, cuisine, tags, difficulty, source)
  └── IngredientItem (name, amount: Double?, unit: Unit?, group: "для теста")
  └── Step (order, text, kind, durationSec?, timerMode, tempC?, ingredientRefs)
```

`Step.kind`: `Prep` (нарезать) | `Action` (помешивать) | `Wait` (ждать закипания).
`timerMode`: `None` | `Countdown` (точно 5 минут) | `Stopwatch` (до золотистого цвета,
с подсказкой «обычно 7–10 мин»).

Встроенный каталог — JSON в `assets/`, который на первом запуске импортируется в Room.
TheMealDB остаётся как необязательный «источник вдохновения» + упражнение на парсинг
текста в шаги (фаза 11).

## 1. Технологический стек

| Что | Чем | Почему |
|---|---|---|
| UI | Compose + Material 3 | декларативность; анимации «ячейка → fullscreen» на View почти нереальны |
| Навигация | Navigation Compose (type-safe routes) | один Activity, состояние живёт выше экранов |
| Состояние | `StateFlow` + immutable `UiState` | LiveData устарела, Flow тестируется и комбинируется |

| Картинки | Coil 3 | Glide сейчас в проекте лишний, удаляем |
| Тесты | JUnit, Turbine, Room in-memory, Compose UI test | логику таймера надо покрыть обязательно |

## 3. Движок готовки — сердце приложения

### 3.1 Главный принцип таймера

**Никогда не считать время переменной в цикле.** Храним абсолютный дедлайн,
а остаток вычисляем как `deadline - now`.

```kotlin
data class CookTimer(
    val id: String,
    val stepId: Long,
    val label: String,
    val totalMs: Long,
    val deadlineElapsed: Long,   // SystemClock.elapsedRealtime() + totalMs
    val deadlineWallClock: Long, // System.currentTimeMillis() + totalMs — для перезагрузки
    val state: TimerState        // Running | Paused(remainingMs) | Finished
)
```

Почему так:
- процесс убили в фоне → восстановили состояние, таймер «сам» на правильной секунде;
- пользователь перевёл часы → `elapsedRealtime` не врёт (он не зависит от настроек времени);
- рекомпозиция Compose не ломает отсчёт;
- остаток — чистая функция, её легко протестировать без Android.

`elapsedRealtime` сбрасывается при перезагрузке устройства — поэтому дублируем wall-clock
и при старте решаем, какой из них валиден.

### 3.2 Параллельные таймеры

Готовка параллельна по природе: вода закипает, пока ты режешь лук. Поэтому
`CookSession` держит **список** активных таймеров, а не один.

```kotlin
data class CookSession(
    val id: String,
    val recipeId: Long,
    val startedAt: Long,
    val doneSteps: Set<Long>,
    val timers: List<CookTimer>
)
```

### 3.3 Где живёт состояние

`CookSessionManager` — `@Singleton`, отдаёт `StateFlow<CookSession?>`, персистится в Room.
**Не в ViewModel экрана готовки**: мини-таймер должен жить, когда этого экрана нет в стеке.
Это важный урок про область видимости состояния.

Отдельно — «тикер» для UI:

```kotlin
val now by produceState(0L) { while (true) { value = SystemClock.elapsedRealtime(); delay(200) } }
```

Правда (дедлайн) и частота перерисовки — разные вещи. Когда UI скрыт, тикер
останавливается сам и CPU не просыпается.

### 3.4 Что происходит, когда приложение в фоне

1. **Живое уведомление без сервиса**: `NotificationCompat.setUsesChronometer(true)
   .setChronometerCountDown(true).setWhen(deadline).setOngoing(true)` — Android сам
   тикает в шторке, нам не нужен ни сервис, ни обновления раз в секунду.
2. **Срабатывание**: `AlarmManager` (`setAlarmClock` / `setExactAndAllowWhileIdle`) →
   `BroadcastReceiver` → короткий foreground-сервис, который звонит и вибрирует.
3. **Разрешения**: `POST_NOTIFICATIONS` (API 33+), точные будильники на API 31+
   (`canScheduleExactAlarms()` + graceful fallback), `BOOT_COMPLETED` для восстановления
   после перезагрузки. Конкретные типы foreground-сервиса сверим с актуальной
   документацией на этой фазе — правила тут меняются почти каждую версию Android.

### 3.5 Анимация fullscreen ⇄ ячейка

Основной путь: `SharedTransitionLayout` + `AnimatedContent`, ячейка и полноэкранный
таймер делят `rememberSharedContentState(key = "timer-$stepId")` через `sharedBounds`.
Compose сам интерполирует размер и позицию.

Запасной путь (если API окажется неудобным): измерить ячейку через
`onGloballyPositioned`, рисовать таймер в оверлее и анимировать `offset`+`scale`.

Детали, которые отличают хорошую реализацию от демки:
- автосворачивание через ~2 с, но тап по экрану удерживает fullscreen;
- уважать «уменьшение анимации» в системных настройках доступности;
- `keepScreenOn` на время готовки (через `DisposableEffect` + `LocalView`).

### 3.6 Мини-таймер

Оверлей уровня приложения:

```kotlin
Box {
    NavHost(...)
    ActiveTimersOverlay()  // читает CookSessionManager, перетаскивается, липнет к углам
}
```

Тап → deep link обратно в сессию готовки. Несколько таймеров — компактный «стек».

## 4. Свои рецепты

- CRUD-редактор: динамические списки ингредиентов и шагов (`LazyColumn` + стабильные ключи).
- Валидация формы в реальном времени, черновики (автосохранение в DataStore).
- Фото: Photo Picker (без разрешений!) → копия во внутреннее хранилище.

  (отличный повод поговорить про дробные значения и форматирование: «1,5 ст. л.»).
- Дублирование встроенного рецепта «в свои» для правок.

## 5. Форум и модерация

Поток: локальный рецепт → предпроверка на клиенте → загрузка → `pending` → модерация →
`published` / `rejected(причина)` → лента.

Четыре слоя модерации:

1. **Клиент** — быстрый фидбек: есть название, ≥2 ингредиента с количеством, ≥2 шага,
   у каждого `Wait`-шага есть длительность, длительности в разумных границах,
   нет дублей, нет ссылок/контактов (спам).
2. **Сервер** — те же правила повторно. Клиенту верить нельзя никогда.
3. **LLM-проверка** (Claude через серверную функцию, со строгой JSON-схемой ответа):
   реализуем ли рецепт, используются ли все ингредиенты, правдоподобны ли время и
   температура, нет ли **опасного** (курица 2 минуты, неправильное консервирование).
   Опасное — автоотказ, спорное — в ручную очередь.
   Ключ API живёт только на сервере, иначе его вытащат из APK.
4. **Сообщество** — жалобы, «я готовил», рейтинг; порог жалоб снимает с публикации.

Плюс: лимит публикаций в сутки на пользователя, дедупликация по хешу содержимого,
модерация картинок, возможность удалить свой контент.

## 6. Мои предложения по фичам

**Сильно повышают ценность (делать):**
- **Список покупок** из одного или нескольких рецептов: объединение одинаковых
  ингредиентов, пересчёт на порции, группировка по отделам магазина.
- **Mise en place** — экран «подготовка» перед готовкой: всё, что надо нарезать и
  отмерить заранее. Так готовят профессионалы.
- **Hands-free режим**: озвучка шагов (TTS), крупный шрифт, листание свайпом,
  экран не гаснет. У повара мокрые руки — это не мелочь, а основной сценарий.
- **История готовки**: «готовил 3 раза», заметки после готовки («в следующий раз меньше соли»).
- **Offline-first**: всё читается из Room, сеть — только синхронизация.

**Интересные (по желанию):**
- **Умное расписание** вместо линейного чек-листа: шаги как граф зависимостей,
  топологическая сортировка и критический путь → «пока вода закипает, нарежь лук».
  Лучшее упражнение на алгоритмы во всём проекте.
- «Что приготовить из того, что есть в холодильнике».
- Импорт рецепта по ссылке (парсинг schema.org/Recipe — почти все сайты его отдают).
- Коллекции/подборки, фильтры по времени/диете/кухне.
- Виджет и Quick Settings tile «вернуться к готовке».
- Расчёт КБЖУ по справочнику ингредиентов.
- Локализация ru/en с самого начала (строки в ресурсах, не в коде).

## 8. Долги текущего кода (фаза 0, уже найдено)

- `implementation(libs.androidx.room.compiler)` — компилятор подключён как рантайм-зависимость;
  должен быть только `ksp(...)`.
- Две разные версии Room одновременно: `2.8.4` из каталога и `2.7.0-alpha11` строкой. Альфа в проекте не нужна.
- Glide **и** Coil, Gson **и** Moshi — по два решения одной задачи.
- `MealViewModel`: мусорный импорт `coil3.util.CoilUtils.result`, `println("ANIME")`,
  `isLoading` не сбрасывается при исключении корректно, ошибка — строка в коде вместо ресурса.
- `ViewModelProvider.Factory` вручную с `as T` — уйдёт вместе с Hilt.
- `AppDatabase.getDb()` создаёт **новый** экземпляр БД на каждый вызов — классическая утечка;
  Room-база обязана быть синглтоном.
- `exclude(group = "org.jetbrains", module = "annotations")` — костыль, разберёмся, нужен ли он.

Это наши первые упражнения: не «переписать», а понять, почему каждое из них — проблема.

## 9. Принятые решения (2026-11-10)

- **Старый код**: чистый старт на Compose. XML-экраны, адаптеры и фрагменты удаляем;
  идеи и история остаются в git.
- **Встроенные рецепты**: свой JSON в `assets/`, импорт в Room при первом запуске.
  TheMealDB — опциональный источник вдохновения, не основа чек-листа.
- **Бэкенд**: Firebase (Auth + Firestore + Storage + Cloud Functions для модерации).
- **Gradle**: один модуль `:app`, слои разделены пакетами; дисциплину границ держим ревью.
